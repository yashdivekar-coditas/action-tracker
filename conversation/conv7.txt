  Gaps worth working on

  1. Stale items never retire. I reproduced this with a crafted note.
     - Rewording a task line ("send the quote" → "send the revised quote")
       creates a second item. The old one stays Open.
     - Deleting a line, or the whole note, leaves its items Open forever.
     - Both go into followup emails, so people get chased for work that no
       longer exists.
     - The only way out is done, and nothing reopens an item. This follows from
       FR-9 and FR-11 plus the "no editing items" scope line, but it is the most
       likely thing to hurt in real use.
     - A fix would be to retire an item on re-ingest when none of its Sources
       still appear in a note. That needs a new FR and a spec.
  2. Gmail has only been exercised against the fake server. technical_details.md
     §6.1 says it was "tested against @artymclabin/gmail-mcp". Nothing in the
     repo shows a live run, and I couldn't do one because it needs OAuth.
     - The adapter has handling that matches the production server's quirks: to
       as a list, Error: text without isError, and the draft id stored as a
       whole sentence. That handling was written from docs rather than a live
       run.
     - Do one real followup "<you>" and check Gmail Drafts before relying on it.
  3. A parenthetical in the owner part leaves the item unassigned. Lena (with 
     Priya) to collect user feedback… becomes Unassigned with the whole line as
     the task. It's per FR-6, but it silently drops a clear owner. Consider
     tolerating (…) after the name.
  4. No README. The setup steps live in docs/technical_details.md §6, so someone
     landing on the repo root has no entry point.

  Smaller caveats

  - Global options position: --db, --config and --today only work after the
    subcommand. actiontrack --db x list gives "invalid choice". The FRD says
    "global options on every command", so it's technically consistent, but
    people will try the other order.
  - Default database: ./.actiontrack.db is relative to the current directory.
    Running from another folder silently uses a different, empty database.
    Setting ACTIONTRACK_DB is the workaround.
  - Mid-batch interruption: if followup --all is killed during the Gmail calls,
    the drafts already made aren't recorded. The 24-hour duplicate warning then
    doesn't fire on the next run.
  - Stale FRD text:
    - FR-7 step 5 cites "(FR-17)" for the roster, but that's FR-18.
    - FRD §8 still lists the Gmail server choice as open, although spec 09
      settled it.
  - Dependency pin: mcp>=2.3 has no upper bound, and gmail.py uses 2.x-only
    imports (Client, mcp_types). A future major release could break followup.
  - Branch clutter: local feat/* branches (all merged), a docs/specs-index
    branch, and a stale current checkout. Switch to main or a fresh worktree
    before new work.

  I did not read store.py, ingest.py or the test files line by line, and I did

  one risk to know is that real Gmail drafts remain unverified.

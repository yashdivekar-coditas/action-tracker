  What we agreed

  Area: Stack
  Decision: Python 3.11+ standard library. The only extra package is the
    official mcp SDK, used just for Gmail. Data lives in a SQLite file
    (./.actiontrack.db, or set --db / ACTIONTRACK_DB).
  ────────────────────────────────────────
  Area: Gmail
  Decision: The tool starts a Gmail MCP server you configure and only ever
    calls its create-draft tool. Never-send is built into the code and covered
    by a test.
  ────────────────────────────────────────
  Area: Config
  Decision: One actiontrack.toml holds the people roster (name, email,
    aliases), the sender name and the server command. Only followup needs it.
  ────────────────────────────────────────
  Area: What counts as an action item
  Decision: Checkbox lines (-, * or + bullets, any indent, [x] or [X]), @name:
    lines, the Owner/Action/Due table, and ACTION: lines. Quoted lines and
    code blocks are ignored.
  ────────────────────────────────────────
  Area: Owners
  Decision: Names are matched against that meeting's attendees, then against
    the roster. If both Priyas attended and the note just says "Priya", the
    owner is ambiguous. A name nobody matches is an unknown owner. "Team"
    means every attendee, "A & B" means both people on one shared item, and
    "TBD", "Someone" or no name means unassigned. Only items with a clear
    owner get a follow-up.
  ────────────────────────────────────────
  Area: Malformed notes
  Decision: A note is skipped and reported if it isn't text, is empty, or has
    no meeting date it can read. Non-.md files are ignored and counted.
  ────────────────────────────────────────
  Area: Due dates
  Decision: Only a trailing "by …", a "due …" or the table's Due column
    counts. The date is worked out from the meeting date (e.g. "by Friday"
    means the next Friday after the meeting). The original wording is always
    kept.
  ────────────────────────────────────────
  Area: Duplicates
  Decision: Same owner(s) and same wording, ignoring case, punctuation,
    "a/an/the" and the due phrase, means one item with several source notes.
    The latest meeting sets the due date. Once an item is done it stays done.
  ────────────────────────────────────────
  Area: Statuses
  Decision: Overdue is worked out each time a command runs. Overdue items also
    count as open. A hidden --today option fixes the date for tests and demos.
  ────────────────────────────────────────
  Area: Commands
  Decision: list shows open items by default and supports --json. done on an
    unknown id fails with exit code 1. followup <owner> also takes --all and
    --dry-run, and creates a new draft every run (warning if one was made
    recently). The email is plain text with overdue items first.
  ────────────────────────────────────────
  Area: ingest
  Decision: Prints a full report and exits 0 even when it skips malformed
    notes.
  ────────────────────────────────────────
  Area: Non-functional requirements
  Decision: Never send email, pytest with a full end-to-end test on the sample
    notes/ folder (Gmail faked), and JSON output. No performance target.

  Assumptions I'll build in unless you object
  1. Item ids stay the same after re-ingesting: they are tied to the source note

  2. "Team" in a note with no attendee list becomes unassigned.
  3. Nested sub-items count as separate items.
